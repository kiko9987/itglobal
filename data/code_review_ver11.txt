
> 총평

  - 새로 추가된 앱 팩토리, 백그라운드 프리패치, SQLite 전환 등 큰 방향은 좋지만, 기존 dashboard/app.py 경로와 새 구조가 동시에 존재하면서 충돌 지점이 남아 있
  습니다. 특히 팩토리 초기화 버그 때문에 새 구조가 실제로는 동작하지 못합니다. 안정화를 위해 주요 모듈을 한 번 더 정리하는 것이 필요해 보입니다.

  Architecture

  - dashboard/__init__.py:37에서 setup_logging(debug_mode=True)를 호출하지만, dashboard/utils/logging_config.py:146의 함수 시그니처에는 debug_mode 인자가 없
  어 TypeError가 발생합니다. 팩토리를 사용하는 실행 경로는 즉시 실패하므로, 인자 이름을 맞추거나 로깅 설정 방식을 다시 연결해야 합니다.
  - dashboard/__init__.py:131는 projects_bp, monitoring_bp만 등록합니다. 새로 만든 dashboard/blueprints/auth.py나 기존에 dashboard/app.py가 직접 들고 있던 라
  우트는 등록되지 않아, 팩토리 기반 실행 시 로그인/관리 API가 사라집니다. 블루프린트 등록을 통일하거나 중복 라우트를 제거해야 합니다.
  - run_server.py:11이 여전히 dashboard.app 모듈의 거대 Flask 인스턴스를 직접 가져옵니다. 새 팩토리를 도입했다면 이 엔트리 포인트부터 from dashboard import
  create_app으로 전환하고 SocketIO 초기화도 팩토리 안에서 처리해야 구조가 한 갈래로 정리됩니다.
  - dashboard/app.py는 19만 라인에 달하는 기존 구현이 그대로 남아 있습니다. 팩토리를 실제로 쓰려면 구형 파일을 축소하거나 단계적으로 제거해 혼선을 줄여야 합
  니다.

  Backend

  - dashboard/__init__.py:34~70 구간에서 환경 검증과 DB 초기화를 잘 정리했지만, BACKGROUND_PREFETCH_ENABLED(dashboard/config/base.py:45)을 읽지 않고 항상 프
  리패치를 켭니다. 테스트/제한 환경에서는 비활성화할 수 있도록 조건을 넣어 주세요.
  - dashboard/utils/background_prefetch.py:102는 start()만 호출하고 즉시 register_sheets_prefetch()를 실행하지만, alert·에러가 발생해도 호출자에게 전파되지
  않습니다. 초기화에서 실패 시 로그만 찍고 넘어가므로, 재시도나 비활성화를 검토해 주세요.
  - API 모니터링은 setup_api_alerts()로 콜백만 등록하고 끝납니다. 임계치 검사 함수 check_api_thresholds()(dashboard/utils/api_usage_monitor.py:291)가 어떠한
  스케줄러에서도 호출되지 않아 알림이 발생하지 않습니다. 백그라운드 쓰레드나 요청 후크에서 주기적으로 호출하도록 설계 보완이 필요합니다.
  - dashboard/utils/api_usage_monitor_new.py가 전체 복사본으로 남아 있습니다. 실제 코드에서 사용하지 않으니 삭제하거나 테스트 전용 위치로 옮겨 중복을 없애
  세요.

  Frontend

  - 서비스 워커 스크립트가 여전히 /static/css/project-list.css, /static/js/project-list.js 같은 레거시 자산을 프리캐시합니다(dashboard/static/sw.js:6). Vite
  빌드 결과가 /static/dist/…로 바뀐 만큼 캐시 목록을 새 산출물 중심으로 재작성하거나, 레거시 파일이 필요하다면 /static/legacy/ 경로로 맞춰 주세요.
  - SERVICE_WORKER_ENABLED 설정(dashboard/config/base.py:49)이 템플릿에서 사용되지 않아 항상 등록됩니다(dashboard/templates/modern_base.html:231). 환경에 따
  라 비활성화할 수 있도록 조건을 추가하면 디버깅과 운영 전환이 쉬워집니다.
  - dashboard/templates/modern_base.html:214~266에 남아 있는 대량의 console.log는 배포 빌드에서 불필요한 노이즈와 개인정보 노출 위험을 만들 수 있습니다. 개발
  모드에서만 출력하거나 최소한으로 줄이는 것이 좋습니다.

  운영 및 안정성

  - 로그 설정은 LOG_LEVEL(dashboard/config/development.py:15, production.py:16)에 의해 결정되도록 하되, 팩토리 초기화가 설정을 덮어쓰지 않도록 정리해야 합니
  다. 현재는 팩토리에서 TypeError 이후 실행이 멈춥니다.
  - 백그라운드 프리패치 종료 처리를 atexit/signal 훅으로 옮긴 것은 좋지만, 멀티프로세스 환경에서 중복 실행을 막기 위해 락이나 상태 체크를 조금 더 견고하게 만
  드는 것이 안전합니다.

  생각

  - 전반적인 방향은 확실히 이전보다 좋아졌고, SQLite 기반 사용자 관리나 Vite manifest 중심의 자산 로딩 등 핵심 성능 이슈도 많이 정리됐습니다. 다만 새 구조와
  기존 구조가 동시에 살아 있어 실행 경로마다 다른 행동을 할 위험이 큽니다. 위에서 지적한 팩토리 오류와 블루프린트 등록 이슈만 해결해도 체감 안정성은 크게 올
  라갈 것입니다.
  - 다음 단계로는 1) 팩토리 기반 엔트리 포인트 통일, 2) 서비스 워커 및 설정 값 연결, 3) API 모니터링 트리거 보완을 추천드립니다. 이후에 dashboard/app.py를 단
  계적으로 축소하면 팀 전체가 훨씬 수월하게 유지보수할 수 있을 것입니다.
