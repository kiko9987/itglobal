전체적 피드백

> 잘하고 있는 점 (Low risk)

  - blueprints/projects.py가 템플릿과 API를 분리해 초기 진입 시에도 경량 데이터만 전달하고, 상세 데이터/통계는 /api/
  projects/**에서 일관되게 내려줍니다.
  - src/js/services/의 DataManager, StateManager, CacheStatusManager, MetadataManager로 기능을 나누어 프런트 로직이 명확
  해졌고, project-list.js는 오케스트레이션만 담당합니다.
  - utils/frontend_helpers.py가 manifest를 우선 로드하고, 실패 시 레거시 자산으로 폴백하면서도 마지막 수정 시각을 확인해
  캐시를 자동 무효화합니다.

  아쉬운 점 (Medium risk)

  - 폴백 매핑이 project-list 중심으로 하드코딩돼 있어 manifest 전체가 비어 있고 다른 페이지(모니터링, 통계 등)가 필요할
  때는 대응이 부족합니다.
  - CacheStatusManager가 cache_health='healthy', prefetch_running=True 같은 더미 데이터를 받도록 고정돼 있어 실제 캐시
  상태와의 괴리가 큽니다. 이후 실데이터로 전환할 때 추가 작업이 필요합니다.
  - 같은 자산 헬퍼를 create_app과 init_frontend_helpers 두 군데에서 등록하고 있어 함수 정의가 중복됩니다. 유지 보수 시
  실수 여지가 있습니다.

  고쳐야 할 점 (High → Medium → Low 순)

  1. High – 폴백 매핑 일반화
      - 현 구조는 main.css, project-list.js 정도만 대응합니다. manifest가 없는 상태에서 다른 화면으로 진입하면 여전히
  CSS/JS가 누락될 수 있습니다.
      - 진행 방향: 폴백 테이블을 페이지별로 확장하거나, 레거시 자산을 폴더 단위로 정리한 뒤 자동으로 매핑할 수 있게 함수
  화하세요.
  2. Medium – 캐시 상태 API/로직 정비
      - 지금은 정상 응답이 항상 “healthy”로 고정돼 있어 프런트 개선이 끝난 뒤에도 실운영 상태를 반영하지 못합니다.
      - 진행 방향: 백엔드에서 실제 캐시/프리페치 정보를 조회하도록 구현하고, CacheStatusManager는 서버 push/polling 두
  모드를 모두 검증하세요.
  3. Low – 헬퍼 등록 중복, 테스트 부재
      - 동일한 헬퍼를 여러 곳에서 등록하기보다는 한 군데에서만 export하고 나머지 호출부는 import만 하도록 단일화하세요.
      - 새 서비스 계층에 대한 최소 단위 테스트(또는 e2e smoke test)를 마련해 회귀를 막는 것도 권장됩니다.

  향후 작업 순서

css 관련 피드백

  1. 폴백 로직을 일반화하면서 레거시 자산 목록을 점검하고, 페이지별로 모던 번들로 전환 가능한지 여부를 확인합니다.
  2. 캐시 상태 API를 실제 데이터 기반으로 바꾸고, 프런트 CacheStatusManager의 server push/polling 경로를 둘 다 테스트합
  니다.
  3. 헬퍼 등록 처리를 단일화하고, 필요한 경우 Jest/Playwright 등의 자동화 테스트를 추가해 새 구조가 깨지지 않도록 안전망
  을 구축합니다.

모던 프로젝트 리스트와의 연계성 평가

> 연계성 평가

  - templates/modern_project_list.html:7에서 get_css_bundle('main')을 통해 새 Vite 번들 css/main.xDfjEebZ.css가 로드되
  고, 그 내부에서 design-system/*, components/* 모듈들을 순차적으로 import 하면서 모듈화된 스타일이 전체 페이지에 적용됩
  니다.
  - manifest.json에 js/components/ProjectTable.js 항목이 css/ProjectTable.dYk2-3uc.css를 함께 적시하고 있어, 테이블 컴
  포넌트 전용 CSS도 자바스크립트 모듈 로딩과 동시에 묶여 내려옵니다. 즉, 모듈화한 CSS가 실제 런타임에 누락 없이 전달되는
  구조가 확보됐습니다.
  - Bootstrap → 토큰 → 컴포넌트 순서로 import 하는 src/css/main.css:3-12와 ProjectTable 전용 CSS가 template의 레이아웃
  (table-section, table-wrapper)과 정확히 맞물립니다. 이름이 변경된 클래스는 템플릿에서도 그대로 사용되고 있으므로 스타
  일이 잘 매칭됩니다.

  아쉬운 부분

  - modern_project_list.html에 여전히 inline 스타일 속성(style="...")이 다수 남아 있어 새 모듈화 방식과 혼용되고 있습니
  다. 이런 인라인 스타일을 컴포넌트 CSS 쪽으로 옮겨야 디자인 시스템이 일관되게 작동합니다.
  - 레거시 폴백 CSS(static/css/project-list.css)는 아직 남아 있고, manifest 실패 시 get_css_bundle이 그쪽으로 떨어집니
  다. 모던 페이지는 거의 새 파일만 쓰지만, 최종적으로는 폴백도 제거할 계획을 세워야 합니다.
  - 전체 CSS 분리는 되었지만, 아직 ProjectFilters나 모바일 카드 등 몇몇 컴포넌트는 공통 토큰을 완전히 활용하지 않고 부분
  적으로 하드코딩한 색상을 사용합니다. 결과적으로 디자인 시스템의 의미가 줄어드는 부분이 있으니 추가 보완이 필요합니다.

  2. 레거시 폴백을 점진적으로 없애고, Vite 번들이 유일한 진입점이 되도록 통합 일정을 잡으세요.

  세요.
