1. QA 테스트의 한계
================================================================================

## 수행한 QA 테스트 방식
❌ 코드 정적 분석 (Static Code Analysis)
  - 파일 읽기 및 패턴 매칭
  - 함수 존재 여부 확인
  - 변수/플래그 검증
  - 로직 흐름 추론

✅ 통과 판정 기준
  - 함수가 정의되어 있음
  - 이벤트 리스너 코드가 존재함
  - 변수가 선언되어 있음
  - 에러 핸들링이 구현되어 있음

## 수행하지 못한 테스트
❌ 실제 브라우저 실행 테스트
  - 버튼 클릭 동작 확인
  - 이벤트 리스너 실제 바인딩 검증
  - DOM 조작 결과 확인
  - 사용자 인터랙션 시뮬레이션

❌ 통합 테스트 (Integration Test)
  - 여러 모듈 간 상호작용
  - 이벤트 전파 확인
  - 타이밍 이슈 감지

❌ E2E 테스트 (End-to-End Test)
  - 사용자 시나리오 기반 테스트
  - 실제 워크플로우 검증

2. 발견된 실제 버그
================================================================================

## 버그: 편집 버튼 클릭 시 편집 모드 진입 안 됨

### 원인
이벤트 리스너 등록 로직 오류:
1. `attachEventListeners()`에서 테이블 클릭만 등록
2. `eventListenersInitialized = true` 설정
3. `openAccordion()`에서 편집 버튼 이벤트 등록 시도
4. 이미 플래그가 true여서 스킵됨
5. **편집 버튼 이벤트가 등록되지 않음**

### 코드 분석으로 놓친 이유
```javascript
// QA 테스트 시 확인한 것
✅ bindCardEvents() 함수 존재 - PASS
✅ 편집 버튼 이벤트 리스너 코드 존재 - PASS
✅ eventListenersInitialized 플래그 존재 - PASS

// 실제로 확인하지 못한 것
❌ bindCardEvents()가 실제로 호출되는지
❌ 호출 타이밍이 적절한지
❌ 조건문으로 인해 스킵되는지
```

4. 이벤트 등록 구조 개선
================================================================================

## 전역 이벤트 (한 번만 등록)
위치: `attachEventListeners()` - 앱 시작 시 1회
- ✅ 테이블 행 클릭 이벤트
- ✅ 편집 버튼 클릭 이벤트 (통합)
- ✅ 저장 버튼 클릭 이벤트 (통합)
- ✅ 취소 버튼 클릭 이벤트 (통합)
- ✅ ESC 키 이벤트
- ✅ 외부 클릭 이벤트

## 프로젝트별 이벤트 (아코디언 열 때마다)
위치: `openAccordion()` - 각 프로젝트 아코디언 오픈 시
- ✅ 총액1 입력 → 총액2 계산
- ✅ 계약금/중도금/잔금 입력 → 미수금 계산
- ✅ 비용 필드 입력 → 마진율 계산

## 왜 분리했는가?
1. **전역 이벤트**: 프로젝트와 무관, 모든 프로젝트 공통
2. **프로젝트별 이벤트**: `projectCode` 클로저 캡처 필요

## 현재 QA 프로세스 (개선 전)
1. 코드 정적 분석
2. 함수/변수 존재 여부 확인
3. 로직 흐름 추론
4. 보고서 작성

→ **실제 동작 검증 없음**

## 개선된 QA 프로세스 (권장)
1. ✅ 코드 정적 분석 (현재 수행)
2. ✅ 단위 테스트 작성 (Jest, Vitest)
   ```javascript
   describe('ProjectRowAccordion', () => {
     it('편집 버튼 클릭 시 편집 모드 진입', () => {
       const accordion = new ProjectRowAccordion();
       const editBtn = document.querySelector('.unified-edit-btn');
       editBtn.click();
       expect(accordion.isUnifiedEditMode).toBe(true);
     });
   });
   ```

3. ✅ 통합 테스트 (Playwright, Cypress)
   ```javascript
   test('프로젝트 편집 워크플로우', async ({ page }) => {
     await page.goto('http://localhost:5000/projects');
     await page.click('tr'); // 아코디언 열기
     await page.click('.unified-edit-btn'); // 편집 버튼 클릭
     await expect(page.locator('input[data-field="총액1"]')).toBeVisible();
   });
   ```

4. ✅ E2E 테스트 (실제 사용자 시나리오)
   - 로그인 → 프로젝트 목록 → 아코디언 열기 → 편집 → 저장
   - 데이터 검증까지 전체 흐름 테스트

5. ✅ 수동 테스트 (최종 확인)
   - 개발자/QA 담당자가 실제 브라우저에서 클릭
   - 예상치 못한 버그 발견

6. 교훈 및 반성
================================================================================

## 잘못된 점
❌ 코드 분석만으로 "100% 통과" 판정
❌ 실제 동작 검증 없이 QA 완료 선언
❌ "함수가 있다 = 작동한다" 오류

## 올바른 접근
✅ 코드 분석은 1차 검증 수단
✅ 실제 브라우저 테스트 필수
✅ 단위/통합/E2E 테스트 자동화
✅ 수동 테스트로 최종 확인

## 향후 개선 사항
1. **Jest/Vitest 도입** - 단위 테스트 자동화
2. **Playwright/Cypress 도입** - E2E 테스트 자동화
3. **CI/CD 파이프라인** - PR마다 자동 테스트
4. **테스트 커버리지** - 80% 이상 목표
5. **실제 사용자 베타 테스트** - 상용화 전 필수
