 개선 아이디어

  - 서비스 계층 분리: dashboard/blueprints/projects.py(특히 2천여 줄 구간)에서 구글시트/캘린더/감사 로그/리드 연동이 한
    함수에 섞여 있습니다. Projects·Sheets·Calendar·Audit 같은 도메인별 서비스 클래스로 나누고 블루프린트는 오케스트레이
    션만 맡기면 유지보수성이 크게 올라갑니다.
  - 구글 시트 I/O 비동기화: 모든 요청이 즉시 Sheets API를 치고 있어서 레이턴시와 SSL 이슈가 반복됩니다. Celery/Redis 큐
    로 캐시 갱신·배경 동기화를 분리하고, API는 캐시/RDB에서 즉시 응답 후 백그라운드에서 Sheets 반영하도록 바꾸면 안정성
    이 개선됩니다.
  - 테스트 체계 보강: 현재는 수동 보고서와 로그에 의존합니다. Sheets API를 googleapiclient.discovery.build에서 추상화한
    레이어를 주입 가능하게 만들고, pytest+responses(moto) 등으로 리팩토링된 헬퍼 함수 단위 테스트를 추가하면 회귀 검증이
    쉬워집니다. 프런트도 /api/projects/* 계약을 대상으로 하는 Playwright/RTL 스냅샷을 두면 좋습니다.
  - 캐시/계약 문서화: smart_get/smart_invalidate 대 invalidate_project_cache 호출 흐름이 파일마다 달라 이해가 어렵습니
    다. 캐시 키·TTL·무효화 규칙을 한 곳에서 정의하거나 README 수준의 계약 문서를 두면 새 기능 추가 때 안전하게 사용할 수
    있습니다.
  - API 계약 일관화: 최근 save_field_memos_batch처럼 계약을 정리한 곳은 좋지만, 여전히 일부 응답이 내부 용어
    (success_count, memo_index 등)를 노출하거나 HTTP 코드가 혼재합니다. JSON 스키마/에러 코드 규칙을 정리하고, Swagger/
    Redoc 같은 스펙 페이지를 자동 생성하면 프런트·외부 자동화가 편해집니다.
  - 관측성/모니터링: SSL/Rate limit 대응 로그는 많은데 결괏값이 센트럴라이즈되어 있지 않습니다. Prometheus/Grafana 또는
    APM(New Relic, Sentry)으로 Sheets 호출 성공률·지연·캐시 적중률을 수집하면 장애 원인 파악이 빨라집니다.
  - 프런트엔드 구조화: Vite 번들 + 전통 템플릿 혼합 상태라 상태 관리가 분산돼 있습니다. SPA 기반 단일 진입(React/Vue)으
    로 옮기고, Socket/캐시/DataManager를 전역 상태(store)로 묶으면 유지보수성이 좋아질 겁니다. 최소한 JS 모듈화를 강화하
    고 공용 컴포넌트/유틸을 패키지화하는 것도 도움이 됩니다.
