  ⚠️ 내가 발견한 리스크 (비판적 검토)

  1. SQLite 동시성 한계 ⚠️

  코덱스 제안:
  # project_locks.db로 락 관리
  INSERT INTO project_locks ...

  문제점:
  SQLite 동시성 모델:
  - 기본 모드: 1 writer OR N readers (exclusive lock)
  - WAL 모드: N readers + 1 writer (개선)

  20명이 동시에 락 획득 시도:
  User 1: BEGIN TRANSACTION → INSERT → 성공
  User 2: BEGIN TRANSACTION → ❌ "database is locked" (5초 타임아웃)
  User 3: BEGIN TRANSACTION → ❌ "database is locked"
  ...
  User 20: BEGIN TRANSACTION → ❌ "database is locked"

  증상:
  - 저장 버튼 클릭 → 5초 대기 → "database is locked" 에러
  - 사용자 경험 악화

  전문가도 알고 있을 가능성: 높음 (하지만 명시 안 함)

  💬 솔직한 의견

  전문가 제안은 기술적으로 우수하지만, 과도할 수 있습니다.

  이유:
  1. 20명 규모는 단일 워커로 충분
    - workers=1 + threads=4 = 동시 4개 요청 처리
    - 20명이 정확히 동시에 저장할 확률 낮음
    - 순차 처리해도 체감 지연 거의 없음
  2. SQLite lock contention은 실제 문제
    - 전문가 제안대로 하면 락 획득/해제가 매우 빈번
    - 20명이 5초 내 동시 저장 → "database is locked" 에러 가능
    - WAL 모드로 완화 가능하지만 완전 해결 어려움
  3. 구현 복잡도 대비 효과 불균형
    - 7개 파일 수정 + DB 마이그레이션 + 테스트
    - vs. workers=1 설정 + Optimistic Lock
    - 효과는 거의 동일 (데이터 손실 방지)

  따라서:
  - 즉시: Option A (최소 구현)
  - 필요 시: Redis 도입 (Option B보다 나음)
