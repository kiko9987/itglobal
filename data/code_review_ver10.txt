  정리 작업 제안

  - dashboard/utils/frontend_helpers.py에서 manifest가 없을 때만 _get_fallback_url을 호출하도록 분기하고, 템플릿에서는 더 이상 조건부 구조를 두지 않는 방향으
  로 정리하세요.
  - 레거시 번들은 /static/legacy/ 등 별도 경로로 옮겨 빌드 산출물과 구분하고, Vite 빌드 시 생성된 .vite/manifest.json만을 단일 진입점으로 사용하면 유지보수성
  이 크게 좋아집니다. 
  - 서브패스로분리하거나, CDN/서비스워커전략을재정리해불필요한로딩로직을줄이세요
  - 4천 줄에달하는 dashboard/app.py는 여전히 뷰서비스관리 API가한곳에몰려유지보수리스크가큽니다. 블루프린트팩토리패턴으로모듈을분할하고설정, 모

> dashboard/app.py를 안전하게 쪼개려면 다음 흐름을 추천합니다.

  1. 앱 팩토리 도입
     dashboard/__init__.py에 create_app()을 새로 만들어 Flask 인스턴스와 공용 초기화(환경 로드, 로거 설정, init_frontend_helpers, init_background_prefetch,
  블루프린트 등록 등)를 담당하게 합니다. run_server.py, 유닛 테스트, WSGI 엔트리가 모두 이 팩토리를 쓰도록 바꾸면 실행 경로가 하나로 정리됩니다.
  2. 블루프린트/모듈 재배치
      - routes/에 projects.py, monitoring.py, auth_admin.py 같은 라우터 파일을 두고 현재 app.py의 뷰·API 구문을 옮깁니다.
      - services/, utils/에 있는 보조 모듈들은 그대로 두되, 각 블루프린트가 필요한 서비스만 가져오도록 import를 슬림하게 조정합니다.
      - 사용자 관리 API(/api/users/*)처럼 현재 if __name__ == '__main__' 내부에 들어있는 항목은 별도 블루프린트로 분리해 앱 팩토리가 언제나 등록하도록 합
  니다.
  3. 초기화 훅 정리
     init_background_prefetch() 같은 동작은 create_app()에서 실행하거나 @app.before_first_request에 연결해 어떤 실행 모드에서도 항상 동작하게 만드세요. 쓰레
  드/세션 정리는 app.teardown_appcontext 같은 곳에 붙이면 메모리 누수를 막을 수 있습니다.
  4. 프런트 자산 단일화
      - modern_base.html은 Vite manifest만 기준으로 JS/CSS를 로드하고, Vite가 없을 때 자동 fallback이 되도록 FrontendAssetManager의 _get_fallback_url()만 남
  깁니다.
      - 레거시 번들은 /static/legacy/…로 옮기거나 서비스워커가 캐시하도록 분리하면 조건부 스크립트가 사라지고 템플릿이 단순해집니다.
      - 서비스워커를 유지한다면 실제 캐시 전략(프리캐시 목록, 업데이트 정책)을 재검토해 Dev 모드에서는 등록하지 않거나, 빌드 시점에만 포함되도록 분기하면 디
  버깅이 쉬워집니다.
  5. 경로·설정 구조화
     settings.py 또는 config/ 모듈을 만들어 Vite 관련 환경 변수, Google API 제한, 캐시 TTL 같은 값들을 한 곳에서 정의하면 배포 환경별 오버라이드가 수월해집
  니다.

  이렇게 단계별로 적용하면 파일 길이를 줄이는 동시에 기능 초기화 시점을 통일할 수 있고, 프런트 로딩 전략도 간결해집니다. 원하는 리팩터링 범위를 알려주시면 구
  체적인 코드 스케치까지 도와드릴게요.

 추가 문제점

  는 가드로 교체해야 합니다.

  전역 로그 설정을 덮어써 전체 앱 로그 레벨이 강제로 INFO로 고정됩니다. 해당 호출을 제거하거나 logger.setLevel(...)처럼 모듈 전용으로만 조정하세요.
