핵심 문제

  - dashboard/auth.py:156에서 사용자 역할을 'Admin', 'Editor'처럼 대문자로 돌려주지만 dashboard/services/
  project_service.py:170는 소문자 'admin'만 검사합니다. 결과적으로 누구나 viewer로 간주되어 편집/생성 버튼과 권한 제어가
  전부 막혀 있습니다. 반환 값을 소문자로 통일하거나 검사 조건을 맞춰야 합니다.
  - dashboard/auth.py:77/85/96/101 등에서 url_for('login_page')로 리디렉션하지만 로그인 화면은 블루프린트 명이 붙은
  auth.login_page입니다. 이 때문에 인증에 실패하면 로그인 화면 대신 Flask BuildError가 발생합니다.
  - 새 진입점(run_server.py)은 팩토리(dashboard/__init__.py)를 부르는데 이곳에선 auth, projects, monitoring만 등록됩니
  다. /, /stats, /receivables와 해당 API는 여전히 dashboard/app_legacy.py 안에만 있어서 새 서버로 띄우면 전부 404가 납
  니다.
  - dashboard/templates/modern_project_list.html:39에서 openNewProjectModal() 같은 옛 글로벌 함수를 호출하지만, 새 Vite
  번들(dashboard/src/js/api/ProjectListAPI.js:15-36)은 그런 함수를 내보내지 않습니다. 레거시 스크립트(dashboard/static/
  legacy/js/project-list.js:7046/7095/9089)를 로드하지 않으면 “정의되지 않음” 에러가 발생해 모달/감사로그/폴더 기능이 멈
  춥니다.
  - dashboard/blueprints/projects.py:145에서 총액·미수금을 project.get('총액', 0), project.get('미수금', 0)으로 더하지만
  시트 매니저(dashboard/utils/google_sheets.py:177, 544)는 '총액 1', '총액 2', '미수금' 등의 컬럼만 제공합니다. 그래서
  헤더 KPI가 항상 0입니다.
  - dashboard/templates/receivables.html:1527, 1800, dashboard/templates/stats.html:715는 여전히 /api/receivables, /api/
  projects/list 같은 레거시 API에 의존합니다. 팩토리 앱에선 이 엔드포인트가 없어서 페이지 로딩 자체가 실패합니다.
  - 사용자 저장소가 이중화되어 있습니다. 팩토리 앱은 dashboard/utils/database.py의 users 테이블을 쓰는데, dashboard/
  auth.UserManager는 별도 SQLite 파일(dashboard/utils/user_database.py)을 사용합니다. OAuth 등이 서로 다른 DB를 읽고 쓰
  는 구조라 동기화 문제가 생깁니다.

  추가 관찰

  - dashboard/app_legacy.py는 200KB가 넘는 모놀리식 코드이고 블루프린트와 기능이 중복되어 유지보수를 어렵게 합니다.
  - dashboard/templates/receivables.html(~1,900줄), dashboard/templates/stats.html(~1,700줄)이 한 파일에 CSS/JS를 모두
  인라인으로 넣어 수정 난이도가 높습니다.
  - dashboard/static/css/project-list.css(92KB), dashboard/static/legacy/js/project-list.js 등 레거시 자산이 남아 새 빌
  드와 혼재합니다.
  - modern_project_list.html이 여전히 base.html을 상속해 레거시 헤더와 중복 CDN을 불러옵니다.
  - new_fastapi_app/ 폴더엔 별도 FastAPI 프로젝트가 있는데 현재 시스템과 연결되어 있지 않은 미완 부분입니다.

  제안

  1. 팩토리 앱과 레거시 앱 중 어느 쪽을 기준으로 할지 결정하고, 아직 옮기지 못한 라우트·API를 마저 이관한 뒤
  app_legacy.py를 정리하세요.
  2. UserManager가 database.py의 저장소를 사용하도록 하거나, 하나의 사용자 DB만 남겨 중복을 제거하세요.
  3. 현대화된 프런트엔드에서 필요한 글로벌 함수는 Vite 번들에서 export하거나, 템플릿에서 호출 방식을 수정하세요. 레거시
  스크립트 삭제는 그 후에 진행해야 합니다.
  4. 통계/수금 템플릿을 Jinja 컴포넌트와 모듈형 JS로 쪼개고, 새 API에 맞춰 리팩터링하세요.
  5. .backup 등 오래된 파일을 정리해 코드베이스 복잡도를 줄이세요.

  완성도 평가
  구조 개편 작업이 활발히 진행 중이지만 레거시와 신구 아키텍처가 동시에 존재하면서 인증, KPI, 수금/통계, 모달 등의 핵심
  기능이 불안정합니다. 현재 상태의 완성도는 약 50 % 수준으로 보이며, 상용 수준 안정성을 위해선 남은 이관과 버그 수정이
  필요합니다.
